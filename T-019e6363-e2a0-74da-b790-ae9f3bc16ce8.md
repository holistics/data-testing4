### Problem Context: TerryWhite Chemmart - relative_period with Date Parameters

The investigation focused on why using a date parameter as a filter inside a metric definition causes `relative_period` to return unexpected results for Last Year (LY) calculations compared to standard date dimension filters.

### Key Findings & Root Cause Analysis
- **Rewriter Limitation**: The `relative_period` rewrite rule shifts time predicates that target the dimension referenced in its first argument. However, `where(... in parameter)` clauses inside a metric definition are treated as literal-bound filters. These are resolved to literals before the shift rule runs, causing the predicate to remain "frozen" (unshifted) while the GROUP BY key is shifted forward. This results in a mismatch between the data scanned and the label produced.
- **Subquery Collapse**: When a parameter filter is applied to a fact table date and `relative_period` is used on that same column, the engine may deduplicate/merge subqueries, causing the shift to be lost entirely (TY and LY values become identical).

### AQL Patterns and Solutions

#### 1. Working Pattern (External Filter)
Filters are applied at the explore/visual level rather than inside the metric definition.
```aml
metric fact_sales_total_sales_amount_ly {
  label: "Sales $ (LY)"
  definition: @aql fact_sales_total_sales_amount | relative_period(dim_date_test_shift_tm.date, interval(-1 year));;
}
// Explore level filter
filters {
  dim_date_test_shift_tm.date matches @(last month)
}
````

#### 2. Non-Working Pattern (Parameter inside Metric)

Applying the parameter filter inside the metric definition breaks the LY shift in the SQL WHERE clause.

```aml
metric fact_sales_total_sales_amount_param_filtered_date_dim_ly {
  label: "Sales $ (LY) (Parameter Filtered | Date Dim)"
  definition: @aql fact_sales_total_sales_amount_param_filtered_date_dim | relative_period(dim_date_test_shift_tm.date, interval(-1 year));;
}
```

#### 3. Proposed Solution: Decoupled Filter Strategy

This pattern sidesteps the rewriter limitation by removing the `where` clause from the LY metric and using a non-null filter at the explore level to enforce the date window.

- **AQL Definition**:
  - `fact_sales_total_sales_amount_param_filtered_date_dim = fact_sales_total_sales_amount | where(dim_date_test_shift_tm.date matches first(dim_date_test_shift_tm.dim_date_filter_param))`
  - `fact_sales_total_sales_amount_param_filtered_date_dim_ly = fact_sales_total_sales_amount | relative_period(dim_date_test_shift_tm.date, interval(-1 year))`
- **Explore Configuration**:

```aml
explore {
  measures {
    fact_sales_total_sales_amount_param_filtered_date_dim_ly,
    fact_sales_total_sales_amount_param_filtered_date_dim
  }
  filters {
    fact_sales_total_sales_amount_param_filtered_date_dim is not null
  }
  params {
    dim_date_test_shift_tm.dim_date_filter_param matches @(last month)
  }
}
```

**Result**: The LY subquery scans the table and shifts the grouping key, while the `is not null` filter on the TY metric (which contains the parameter filter) clips the result set to the correct overlapping window during the FULL JOIN.
